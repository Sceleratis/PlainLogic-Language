# Implementing PlainLogic and specifications

Use this mode for bare input/path invocations and requests to implement, compile, convert, or build. "Compile" means agent-guided translation into real code; it does not promise deterministic compilation, execution, or formal verification.

Read and apply [semantic validation](validation.md) before implementation edits. Accept full/informal PlainLogic, mixed English and exact logic, or specs and requirements documents. Resolve the intended behavior, current repository instructions, target context, relevant source, and current diff. Preserve existing user changes. Reuse a current assessment covering the same logic and source, rechecking only changed or unverified behavior.

For a specification, extract its actual decisions and map them to the requested implementation. Make consequential branches, effects, errors, and unresolved choices reviewable in a short logic sketch or explanation when useful. A separate full `.plog` document or user approval round is not required. Do not manufacture missing decisions while turning a spec into apparently complete logic. A request only to draft pseudocode must stay in authoring mode.

For whole `.plog` or spec input, preserve the input file by default and create or modify idiomatic target-language files in the repository. Resolve output locations from explicit user instructions, verified `ref` mappings, existing interfaces, and repository conventions. Reuse existing routines rather than creating duplicates. A bare `.md` path is a specification input in this mode; it is not an instruction to rewrite its documentation or every code example. For PlainLogic embedded in actual source, follow [conversion](conversion.md).

Infer the target from a clear source extension, existing project, supplied target declaration, and selected host. Respect target-specific versions and conventions. If credible targets or output mappings lead to materially different results, ask one consequential question before the dependent edits. Do not choose a language, overwrite an unrelated file, or create a new application arbitrarily to satisfy a bare path.

Resolve symbolic types, `ref` locators, and port bindings against source. A port is a behavior contract, not proof an API exists. Prefer existing interfaces and utilities over invented adapters or dependencies. For canonical documents, run `python <skill-directory>/scripts/check_plainlogic.py <file> --ready`; structural success cannot replace semantic validation. Review informal fragments directly. If the checker is unavailable, manually inspect structure and disclose the limit.

Preserve exact conditions, rounding, ordering, errors, null handling, return arity, and effects. English `>` steps are ordered behavior to implement, including whole loops and central business logic. Resolve ordinary mechanics through existing code conventions without first expanding every sentence into another pseudocode draft. Do not add unrequested retries, caching, concurrency, validation policy, endpoints, or fallbacks. Necessary nearby support and equivalent algorithms are implementation choices within the authorized behavior.

Read [extension surfaces](extensibility.md) for aliases, native text, and target-specific capabilities. Implement aliases according to verified runtime behavior, including body scope, capture, scheduling, control transfers, and failures where material. Strip only a native block's container margin when adapting literal source; preserve meaningful internal whitespace and content. Do not reduce a target-specific interface or guarantee just to fit the common grammar.

An `open`, `ask`, contradictory requirement, or materially undefined operation blocks its dependent slice. Ask the focused question and continue independent ready work when useful. Preserve the remaining draft. Do not implement unknown behavior as a guessed return, default, silent no-op, or exception that was never requested. Later user instructions can revise the contract; make consequential revisions visible and continue from the updated intent.

Implement the smallest complete authorized slice. Document public interfaces and non-obvious behavior when useful. Use supplied cases as candidate behavioral checks; add focused coverage for meaningful boundaries and effects when warranted. Follow repository test conventions and filter the project's test run to the specific tests needed. Keep verification proportional and avoid tests that merely mirror implementation structure.

Before finishing, compare the actual diff to the requested logic, relevant requirements/coverage, ports, and source conversion boundaries. Report implemented behavior, useful routine-to-symbol/check mappings, checks actually run, and unresolved limits. A partial ready slice must be identified as partial. No document readiness label grants permission to commit, push, deploy, publish, or perform external mutations.
